# 问题分类器（Question Classifier）与意图路由

适用节点：`问题分类器`（Question Classifier）、`条件分支`（IF/ELSE）、`代码执行`（关键词匹配）。
适用场景：对话流的意图分流层——决定本轮请求走知识库、走接口、走陪练、走闲聊还是走兜底。

---

## 一、先理解节点本质

`问题分类器` 表面是功能节点，底层是**一次模型调用**。平台在后台给它下死命令：只输出纯净 JSON（如 `{"class": "Class 3"}`），不许说废话。

由此推出三条基本判断：

1. 分类器的稳定性 = 所选模型的指令服从能力
2. 分类器每次运行 = 一次模型推理 = **1~2 秒冷启动延迟**
3. 分类器的输入输出都是变量，可以承载额外字段（见第五节）

---

## 二、配置要点

### 1. 分类数量与粒度

分类数不是越多越好。粒度按**下游处理路径**切分，同一路径的问题合并为一类。

| 切分依据 | 是否单独成类 |
|---|---|
| 走不同下游节点（知识库 / 接口 / 陪练 / 固定话术） | 必须单独成类 |
| 只是问法不同、下游完全一致 | 合并 |
| 闲聊与超范围提问 | **必须拆成两类**，见第三节 |
| 同一对象但一动一静（实时排班 vs 静态简历） | 必须拆，见第四节 |

### 2. 分类描述（Description）写法

描述是模型做分类的唯一依据，也是延迟的主要成本。

- 每条描述写：**适用场景 + 典型输入示例**
- 示例用用户真实会说的话，不要用书面语
- 只写判别所需的区分特征，不要写业务背景
- 两个分类的描述不能语义重叠，否则模型会摇摆

反例（过长，拖慢推理）：

```text
询问公司介绍、餐厅、Wi-Fi密码、停车位、闲聊，如洗手间在哪、附近有什么吃的……
```

正例（压缩到核心词，实测推理速度提升约 30%）：

```text
大堂设施、网络、问路、闲聊。
```

### 3. 模型选型

| 分类器承担的工作 | 模型选择 |
|---|---|
| 只输出一个类别编号 | `flash` / `mini` / `lite` 级（如 `Doubao-lite`、`qwen3.5-flash`），追求速度 |
| 需要严格 JSON 输出，或同时输出关键词 | 强指令服从模型（如 `Doubao-pro`、`GLM-4`、`GPT-4o`、`Claude-3.5`） |
| 需要多步推理判断 | 不放在分类器里做，拆到下游 LLM 节点 |

**同一工作流内不同节点可以使用不同模型。** 闲聊回复用便宜小模型，分类器与信息提取用强模型，这是常规做法，不必全局统一。

**禁止**给分类器选 `max` 或带思考链的大参数模型——分类是短任务，思考链只增加延迟。

### 4. ELSE 分支必须存在

分类器必须配一个 `ELSE` / 默认出口，接兜底回复。所有分类都未命中时，请求不能悬空。

---

## 三、闲聊必须拆成两类

### 1. 错误做法

只设一个"闲聊 / 无关问题"分类，把"你好"和"周杰伦老婆是谁"放进同一类。

后果：超范围提问被闲聊话术接走，机器人对无厘头问题热情自我介绍，边界感全无；或反过来，用户打招呼收到冷冰冰的"知识库暂未收录"。

### 2. 正确做法：双闲聊分流

| 分类 | 描述 | 下游 |
|---|---|---|
| Class 4：礼貌打招呼 | 纯粹的打招呼、寒暄或日常问候。例如"你好""哈喽""在吗""早上好""你好呀"，没有提出任何具体业务或知识问题 | 固定欢迎话术（介绍身份 + 服务范围 + 询问需求） |
| Class 5：超出范围无关提问 | 用户提出了具体提问，但该提问与本院、医疗、健康、业务范围完全无关。例如问娱乐明星、科学常识、天气、数学题 | 固定拒绝话术（声明服务边界 + 拉回业务范围） |

实现方式：两个分类各接一个 `直接回复` 节点，**不新增 LLM 节点，零额外延迟**。

### 3. 三路分明的最终效果

| 输入类型 | 走的分类 | 回复基调 |
|---|---|---|
| "哈喽在吗" | Class 4 礼貌打招呼 | 热情、有温度 |
| "周杰伦老婆是谁" | Class 5 超范围 | 礼貌拒绝，强行拉回业务 |
| "你们医院今天能停车吗" | Class 2 业务查询，但知识库返回空 | 严谨兜底，给替代方案 |

第三类与第一、二类的区别在于：**它确实进了业务分支，只是检索为空**。兜底话术要覆盖这一类，不要和超范围拒绝话术混用。

## 四、按数据通道拆类（动静分离）

同一业务对象的属性，如果实时性要求不同，必须在分类层就拆开。

| 分类 | 描述 | 通道 |
|---|---|---|
| Class 2：实时排班与号源查询 | 仅用于查询实时出诊排班、星期几上班、今天有没有号、号源剩余等动态时间信息 | 参数提取 LLM → HTTP 请求 → 代码清洗 → 播报 LLM → 直接回复 |
| Class 5：专家介绍与科室位置 | 专门用于查询详细介绍、简历、擅长领域、职称，以及科室介绍、科室在几楼等静态背景信息 | 知识检索 → 播报 LLM → 直接回复 |

不拆的后果：用户问"儿科急诊在哪"，系统走实时号源分支，回复里夹带排班信息；或用户问"详细介绍某医生"，接口里没有简历字段，只能回"查不到"。

**接口负责实时性，知识库负责丰富性。分类层是唯一能实现这个分工的位置。**

---

## 五、分类器兼产检索关键词

分类器本来就要跑一次推理。让它同时输出改写后的检索关键词，几乎不增加延迟，一次解决上下文补全与术语翻译。

```text
请根据历史对话，判断用户的最新输入属于哪个分类（1/2/3/4）。
同时，提取出最重要的搜索关键词（把大白话转化为专业术语，补全上下文中的名字）。
请严格输出 JSON 格式：
{"class": "2", "keywords": "儿童保健科 刘慧娟 医生 排班 出诊时间"}
```

下游 `知识检索` 节点的查询变量改用 `keywords` 字段，不再用 `sys.query`。

**前提条件**：JSON 结构化输出要求模型指令服从能力强。用 mini 级小模型会直接触发 `invalid json object`。若平台只能用小模型，走第六节的防弹版方案，或改用知识库埋词（见 `knowledge.md`）。

## 六、分类器报错的两条出路

### 报错原文

```text
got invalid json object. error: Extra data
```

### 根因

小模型（如 `Doubao-Seed-2.0-mini`）服从性弱，在 JSON 后面多说了话：

```text
{"class": "Class 3"} 好的，我已经为您分类好了！
```

多出的自然语言破坏了 JSON 结构，平台解析失败。**这不是连线问题，是模型能力边界问题。**

### 出路一：换更强的模型（首选）

打开报错的 `问题分类器` 节点，把模型从 mini 级换成参数更大、指令服从更强的模型，重跑即可。配置成本最低。

### 出路二：手工搭防弹版分类器

适用于平台锁定小模型、或换模型后仍偶发报错的情况。

**步骤：**

1. 删除 `问题分类器` 节点
2. 原位置换成普通 `LLM` 节点

```text
SYSTEM：
请根据用户的输入，判断他的意图属于以下哪一类，并【只输出数字，不要输出任何其他标点或汉字】：
1 - 业务知识查询
2 - 开启模拟沟通陪练
3 - 开启专项训练
4 - 查看复盘报告

USER：
{{sys.query}}
```

3. 后面接 `条件分支`（IF / ELIF），**判断条件用「包含」而不是「等于」**

| 分支 | 条件 | 去向 |
|---|---|---|
| IF | `LLM.text` 包含 `1` | 知识库答疑 |
| ELIF | `LLM.text` 包含 `2` | 模拟沟通 |
| ELIF | `LLM.text` 包含 `3` | 专项训练 |
| ELIF | `LLM.text` 包含 `4` | 查看复盘报告 |
| ELSE | 以上都不满足 | 兜底回复 |

**防弹原理**：即使小模型抽风输出"我觉得是类别 3 哦"，条件分支抓到 `3` 仍能正确流转，不会抛 JSON 解析错误。代价是多两个节点。

> 注意：若分类编号可能出现在其他数字文本中（如用户原话含数字），改用「包含 `3`」会有误判风险。此时在 LLM 提示词里要求输出固定前缀（如 `CLASS:3`），条件分支判断包含该前缀。

## 七、分类器 1~2 秒延迟的三类解法

延迟来源：分类器是一次模型推理。用户说完话到业务分支开始执行之间，存在 1~2 秒空窗。**分支内的垫话救不到最前面**，因为此时还没走到分支。

### 解法一：快车道分流（效果最强）

现实中约 70% 的高频问题不需要动用模型。用耗时 2ms 的 `条件分支` 或 `代码执行`（Python 关键词匹配）直接截胡。

```text
【开始】
   ↓
【条件分支：关键词快车道 (2ms)】
   ├── 包含(洗手间|厕所|wifi|密码) ──→ 【大堂问答】(10ms 秒回)
   ├── 包含(快递|外卖|送餐) ────────→ 【外卖指引】(10ms 秒回)
   ├── 包含(带我|导航) ────────────→ 【物理带路】(10ms 秒回)
   │
   └── ELSE（复杂长句、商务找人）──→ 【大模型问题分类器】(1.5s)
```

要点：
- 关键词表按真实高频问题维护，定期从日志补词
- 命中即返回，绝不进入分类器
- 只有真正复杂的请求才付那 1.5 秒

### 解法二：口癖垫话（心理学手段）

在分类器旁**并行**挂一个 `直接回复` 节点，分类器开始推理的同时先把垫话吐给前端。

内容不要写"正在为您查询……"——回答"洗手间在哪"时极度违和。改成人类思考时自然吐出的语气词：

```text
好的，
```

或

```text
在的，
```

听感拼装：

```text
第 0.05 秒  前端开口："好的，"
第 1.5 秒   分类器完成，业务分支输出："洗手间在左侧茶水间拐角处。"
用户听到    "好的，（自然停顿）洗手间在左侧茶水间拐角处。"
```

技术延迟被包装成人类说话的思考顿挫。**垫话必须与业务场景无关，否则任意场景都会违和。**

### 解法三：给分类器减负

| 动作 | 效果 |
|---|---|
| 压缩每条分类描述到核心词 | 实测推理速度提升约 30% |
| 锁死 `flash` / `mini` / `lite` 模型 | 避免思考链开销 |
| 删除描述里的业务背景与长句示例 | 减少输入 token |
| 分类数量控制在必要范围 | 减少候选空间 |

### 组合建议

工业界最优组合是 **快车道 + 口癖垫话**：高频问题 10ms 秒回，复杂问题用垫话抹平空窗期。两者都不增加模型调用。

## 八、分类与兜底的关系

分类器会漏判、会错判。必须有机制接住，且接住的位置不止一层。

| 层级 | 兜底手段 | 接住什么 |
|---|---|---|
| 分类器层 | `ELSE` / 默认出口 → 兜底回复 | 所有分类都不匹配的输入 |
| 业务分支层 | 检索为空时的固定话术 | 分类正确但数据缺失 |
| 分支内条件 | `条件分支` 判断关键字段（如是否等于 `NONE`） | 提取失败、接口无结果 |
| 提示词层 | 明确"查不到时只能回复固定话术，禁止编造" | 抑制幻觉 |

### 关键约束

1. **ELSE 出口必须连到话术，不能连回分类器**，否则形成死循环
2. **兜底话术必须比分类描述更宽**。兜底话术过窄会把单点失败放大成体验事故——例如兜底只写"暂未收录该科室的详细挂号信息"，用户问"详细介绍某医生"时就会答非所问
3. **兜底话术要区分场景**：超范围拒绝话术 ≠ 知识缺漏话术 ≠ 接口失败话术。三者在分类层就已分流，不要复用同一段文案
4. **兜底话术要给替代方案**（转人工、打电话、现场咨询），不要只声明"查不到"

## 九、排查顺序

```text
分类结果不对
  ↓
1. 看节点运行日志，确认模型实际输出的类别
  ↓
2. 输出格式崩了（JSON 报错）→ 换强模型 / 改防弹版
  ↓
3. 输出合法但分错 → 检查分类描述是否语义重叠、示例是否够
  ↓
4. 偶发分错 → 检查是否 mini 级模型，考虑升级
  ↓
5. 分类对但体验差 → 查分支内兜底话术与变量引用
  ↓
6. 分类对但慢 → 快车道 / 垫话 / 压缩描述
```

分类器只负责"往哪走"。走到分支之后的问题，回 `knowledge.md`、`prompt-design.md`、`integration.md` 查。
