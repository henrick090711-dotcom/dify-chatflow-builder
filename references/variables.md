# 变量体系与变量流转（Dify Chatflow / 某智能体平台）

适用：在 Chatflow 画布上做状态机、多轮记忆、跨节点传参时，先读本文件，再动节点。

---

## 1. 变量类型体系

先判断"这个值活多久、给谁看"，再决定用哪种变量。选错类型是绝大多数"状态不生效"的根因。

| 类型 | 创建位置 | 作用域 | 生命周期 | 赋值方式 | 典型用途 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 系统变量 `sys.query` | 平台内置，开始节点默认带出 | 单次请求 | 单轮 | 不可写 | 用户当前这句话 |
| 环境变量 | 应用级配置 | 全应用、全会话 | 永久 | 平台配置页填写 | API Key、固定端点、机构 ID |
| 会话变量（Conversation Variables） | 画布左侧【变量（Variables）】面板 | 单次会话 | 当前聊天内有效，重新聊天即清空 | 只能由【变量赋值】节点写 | 状态机 `current_mode`、累计日志 `weakness_log`、暂存要素 |
| 节点输出变量 | 每个节点自身产生 | 仅下游节点可见 | 单次运行 | 由节点执行产生，不可手写 | 上游结果传给下游 |
| 开始节点自定义参数 | 【开始节点】右上角 `+` 新增 | 本次运行 | 单次运行 | 调用方传入（表单/工具调用） | `target_person`、`visitor_name`、`visitor_phone` |

判断分支：

- 需要跨轮记住 → 建**会话变量**。
- 只在一次运行内从 A 传到 B → 用**节点输出变量**，不要建会话变量。
- 是密钥、固定地址、机构号 → 建**环境变量**，不要塞进会话变量，也不要在代码里硬编码。
- 是用户这一句话 → 直接用 `sys.query`。

反面结论（已踩实）：出现"状态在条件分支里找不到"时，**不要去建环境变量**。这类问题与会话状态无关，建环境变量不解决任何问题。

会话变量在建应用时先一次性规划完，按状态机语义命名并给默认值：

| 变量名 | 类型 | 默认值 | 语义 |
| :--- | :--- | :--- | :--- |
| `current_mode` | String | `idle` | `idle` 空闲 / `rp_setup` 陪练配置 / `rp_active` 陪练中 / `quiz_setup` 训练配置 / `quiz_active` 训练中 |
| `task_stage` | String | `idle` | `idle` / `collecting` / `waiting_nav` / `navigating` |
| `rp_scenario` | String | 空 | 客户画像 |
| `quiz_topic` | String | 空 | 训练专项，如"携号转网" |
| `weakness_log` | String | 空 | 累计薄弱点 |
| `visitor_name` / `visitor_phone` / `target_person` / `target_email` | String | 空 | 访客三要素与通讯录命中结果 |

默认值不是装饰：`current_mode` 默认 `idle` 决定第一轮对话走哪条分支。留空会导致条件分支全部不命中，直接落到 ELSE。

## 2. 变量生命周期：定义、赋值、引用三处必须对齐

同一个变量名必须在以下三处逐字一致，任一处拼错即静默失效。

| 环节 | 位置 | 操作 | 检查点 |
| :--- | :--- | :--- | :--- |
| 定义 | 左侧【变量（Variables）】面板 | 新建会话变量，选类型，填默认值 | 名字大小写、下划线 |
| 赋值 | 【变量赋值】节点 | 覆盖模式选变量 / 设置模式填文本 | 框内不得出现 `=` 与手打 `{{ }}` |
| 引用 | 提示词 `{x}`、条件分支变量下拉、工具节点参数 | 插入带底色气泡 | 必须是气泡，不能是手打文本 |

对齐失败的两类典型表现：

1. 提示词里写 `请回答以下关于【quiz_topic = sys.query】的考核问题` → 大模型把 `quiz_topic = sys.query` 原样念出来。原因是该串是纯文本，不是变量气泡，系统不替换。
2. 条件分支里只有 `text` 可选，找不到 `is_complete`。原因是上游是 LLM 节点，LLM 的输出永远只有一个 `text`（String），JSON 内部字段不会成为可选变量。

引用范围规则：

- 节点输出变量只对**下游**节点可见。上游节点、平行分支看不到。
- 代码节点的输出变量若未在界面登记，下游下拉里根本不会出现（详见第 6 节）。
- 会话变量在任何节点都可引用，但只有在【变量赋值】节点执行过之后才持有新值。

## 3. 【变量赋值】节点：覆盖与设置两种模式

平台把两种模式做了硬性互斥，先认模式，再填内容。

| 模式 | 可填内容 | 限制 | 适用 |
| :--- | :--- | :--- | :--- |
| 覆盖（Overwrite） | 只能选**一个**纯变量 | 文本框被平台没收，不能打字 | 把上游输出或 `sys.query` 原样搬进会话变量 |
| 设置（Set） | 只有文本框，可手打文本 | `/` 快捷键被屏蔽，`{x}` 按钮被没收，**无法插入变量气泡** | 写死常量，如 `idle`、`quiz_active` |

决策分支：

- 要写入常量 → 选【设置】，框里只填纯值，如 `idle`。不要写 `current_mode = idle`。
- 要搬运变量 → 选【覆盖】，在下拉里选目标变量气泡，如 `sys.query`。
- 要"旧值 + 新值"拼接 → 两种模式都做不了，走第 4 节的模板转换节点。

正确与错误写法对照：

```text
# 错误：变量赋值 5 的设置框
quiz_topic = sys.query          -> 变量里存进整串英文字母，大模型照念
current_mode = quiz_active      -> 状态永远不等于 quiz_active，闭环不退出

# 正确：常量用设置模式
current_mode                    -> 设置模式，框内只填：quiz_active

# 正确：搬运用覆盖模式
quiz_topic                      -> 覆盖模式，选中 sys.query 气泡
```

批量排查：把所有【变量赋值】节点逐个点开，凡框内出现 `=`、`{{ }}`、`\n` 的一律净化。素材中出现过的待净化节点包括 `变量赋值 2`、`变量赋值 3`、`变量赋值 6`、`变量赋值 7`。

## 4. 变量拼接：为什么直接拼接失败

失败原因链：

1. 设置模式的文本框不支持 `{x}`，也屏蔽 `/`，插不进变量气泡。
2. 手打 `{{weakness_log}}` 不被识别。Dify 只认带底色的变量气泡，手敲大括号会被当普通字符。
3. 手打 `\n` 不会换行。文本框里必须直接敲回车键做真实换行。
4. 引用不存在的节点（如 `{{客户模拟与裁判.text}}`）会得到空值，因为画布上没有该节点。

结论：**拼接与存储分离**。先让模板转换节点拼好整段文本，再用【覆盖】模式一次性写回会话变量。

标准三步：

```text
第一步 插入【模板转换】节点（Template / 文本处理），放在变量赋值节点之前
第二步 模板转换内用 {x} 插气泡：
        [weakness_log 气泡]
        模拟场景薄弱点：[LLM 4 气泡]
第三步 变量赋值节点改用【覆盖】模式，选中 {{模板转换节点.result}}
```

模板转换节点的语法是 jinja2，需要动态值时可写 `{{name}}`，并把 `name` 在节点输入变量里绑到上游气泡：

```jinja2
好的，已经通过飞书为您通知了 {{name}} 老师，请您在休息区稍坐片刻！
```

模板转换节点的两条硬规则：

- 必须至少绑定一个输入变量，否则校验不通过。只需要固定文案时，绑一个存在但不使用的变量（如 `temp` = `sys.query`）即可通过校验，正文照常手写。
- 输出变量名通常是 `result`（String）。引用时用气泡选，不要手打。

为什么更稳：模板节点执行不调模型，毫秒级；拼接逻辑集中在一处，后续要加时间、加客户画像只改这一个节点；变量赋值节点退回纯搬运，不再承担拼装职责。

## 5. 变量清理与重置

会话变量不会自动回退。必须显式写回，否则状态永久停留。

必须清空或回写的时机：

| 时机 | 必须执行 | 漏掉的后果 |
| :--- | :--- | :--- |
| 任务型闭环结束（成功/失败/超时） | 变量赋值把 `current_mode` 或 `task_stage` 写回 `idle` | 永远困在陪练/登记闭环，用户说"你好"仍被当成客户 |
| 进入新任务前 | 重置上一任务的暂存要素 | 上一轮姓名、电话串到新访客，飞书发给错人 |
| 累计型变量（`weakness_log`）写完后 | 报告生成后清空或归档 | 记录无限增长，最终超出上下文 |
| 分流到纯问答分支 | 不写状态即保持 `idle` | 若误写状态，闲聊分支被状态机拦截 |

规则：

- 条件分支的每个出口都要有归宿。IF 命中后必须紧跟【变量赋值】改状态，再接【直接回复】；只回复不改状态等于没退出。
- 累计日志漏清的直接症状是"薄弱点日记本记下一堆乱码"——因为写进去的是未替换的代码文本，不是真实内容。
- 会话变量只在当前聊天有效，重新开会话自动清空。因此测试前先新开会话，避免用脏状态判断节点是否配错。

## 6. 代码节点的输入/输出变量登记

代码节点实行"海关申报制"：Python 里算出来的东西必须在界面登记，否则下游看不见。

输入侧：

| 项 | 要求 |
| :--- | :--- |
| 变量名 | 默认是 `arg1`，必须改成有语义的名字，如 `llm_text`、`user_query`、`http_result` |
| 变量值 | 点右侧输入框用 `{x}` 选上游气泡，不能留空 |
| 类型 | `text` 传纯字符串；`json` 直接传 Python dict / list，字段取值无需 `json.loads` |

输出侧：

| 项 | 要求 |
| :--- | :--- |
| 登记 | 在【输出变量】区点 `+` 逐个新增，类型默认 String |
| 命名 | 必须与 `return {...}` 的 key 逐字一致 |
| 数量 | 登记项与 return 项必须一一对应，不多不少 |

三种报错直接对应三种错配：

```text
Not all output parameters are validated.
-> 代码 return 了界面未登记的 key（例：登记 result，代码多返回 pure_url）

Output result is missing
Output form_output is missing
-> 界面登记名与 return 的 key 不一致（例：登记 form_output，代码 return form_result）

下游变量下拉里只有 result、找不到 target_person / visitor_name / visitor_phone
-> 输出变量区只登记了 result，其余未申报
```

代码骨架固定写法：

```python
import json, re

def main(**kwargs):
    raw = str(kwargs.get("llm_text", ""))          # 入参名 = 界面输入变量名
    try:
        m = re.search(r'(\{[\s\S]*\})', raw)
        data = json.loads(m.group(1)) if m else {}
        target = data.get("target_person") or "相关老师"
        return {"target_person": target}           # key = 界面输出变量名
    except Exception:
        return {"target_person": "相关老师"}        # 异常也要返回同名 key
```

当输入类型选 `json` 且上游是 `Array[Object]` 时，先做类型兼容再取字段：

```python
raw_mcp = kwargs.get("mcp_output", {})
if isinstance(raw_mcp, list) and raw_mcp:
    data = raw_mcp[0]
elif isinstance(raw_mcp, dict):
    data = raw_mcp
else:
    data = json.loads(str(raw_mcp))
```

## 7. 开始节点参数化：用明确参数替代 LLM 提取

把模糊输入拆成业务参数，可直接删掉一个 LLM 提取节点。

改造前（缺信息且慢）：

```text
【开始 mingzi】->【LLM 提取姓名】->【知识检索 通讯录】->【LLM 提取邮箱】->【发飞书】
```

改造后（4 秒降到 1.5 秒）：

```text
【开始 target_person / visitor_name / visitor_phone】->【知识检索 通讯录】->【LLM 提取邮箱】->【发飞书】
```

操作步骤：

1. 打开【开始节点】，删掉模糊参数 `mingzi`。
2. 点右上角 `+`，新增 String 参数并写清描述：`target_person`（被访员工姓名）、`visitor_name`（访客真实姓名）、`visitor_phone`（访客手机号）。
3. 删除画布上的【LLM 提取姓名】节点，把开始节点直接连到【知识检索】。
4. 【知识检索】的 Query 改成 `{x}` 选 `target_person` 气泡。
5. 工具节点（飞书）的消息内容直接用 `visitor_name`、`visitor_phone` 气泡。

为什么调用方会自动填对：把工作流【发布为工具】后，Dify 把开始节点的参数名和中文描述打包成标准工具接口。主 Agent 拿到表单 JSON 时按字段语义自动对号入座（张三 → `visitor_name`，138... → `visitor_phone`，李总 → `target_person`）。参数描述写得越具体，自动填充越准。

判断分支：

- 上游能提供结构化字段 → 用开始节点参数，禁止再加 LLM 提取。
- 上游只给一句自然语言 → 保留 LLM 提取，但把输出用【变量赋值】暂存，供多分支复用。

## 8. 引用变量的三种入口

| 入口 | 操作 | 禁止 |
| :--- | :--- | :--- |
| 提示词（SYSTEM / USER） | 光标定位后点 `{x}`，或输入 `/` 触发列表 | 手打 `{{变量名}}` |
| LLM 顶部【上下文】 | `{x}` 选知识检索的 `result`（Array[Object]） | 把 `sys.query` 塞进上下文 |
| 条件分支 / 工具参数 / 代码输入 | 下拉选择气泡 | 手打节点名与字段名 |

知识检索结果的处理：`result` 是 `Array[Object]`，不能直接进 SYSTEM。先放进 LLM 顶部的【上下文】，平台会自动拼成纯文本，再在提示词里用 `{x}` 插上下文气泡（模板写法 `{{#context#}}`）。上下文框留空时，`{{#context#}}` 为空白，模型只能靠常识作答。

## 9. 交付前自检清单

| 检查项 | 通过标准 |
| :--- | :--- |
| 会话变量表 | 名字、类型、默认值齐全，状态机默认值写 `idle` |
| 变量赋值节点 | 全部无 `=`、无手打 `{{ }}`、无字面 `\n` |
| 模式选择 | 常量用设置、搬运用覆盖、拼接走模板转换 |
| 闭环出口 | 每个 IF/ELIF 分支都有变量赋值回写 `idle` |
| 代码节点 | 输入变量已改名并绑定气泡；输出变量已登记且与 return key 一致 |
| 开始节点 | 参数为业务字段，每个都有中文描述，无残留 `mingzi` |
| 引用形态 | 所有变量引用均为气泡，无手打文本 |
| 测试环境 | 新开会话测试，避免旧会话变量干扰 |
