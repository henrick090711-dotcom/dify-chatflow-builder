# 知识库检索：失效模式、调优与替代方案

适用节点：`知识检索`（Knowledge Retrieval）、`问题优化`（Question Optimizer / Query Rewrite）、`LLM` 的顶部上下文输入框。
适用范围：企业知识库问答类对话流（导诊、前台、内部通讯录、产品答疑）。

---

## 一、先分清责任层：谁在失忆

排查召回失败前，先定位故障在哪一层。三层混淆会导致改错地方。

| 层 | 节点 | 是否具备多轮记忆 | 失效表现 |
|---|---|---|---|
| 回答层 | LLM 节点 | 开【记忆】后有 | 记得上文，但资料为空，只能说"查不到" |
| 检索层 | 知识检索节点 | **永远没有** | 拿"他什么时候有号"原句去搜，搜不到 |
| 数据层 | 知识库切片 | 不涉及 | 命中了，但命中片段内容为空 |

**关键结论：记忆开关救得了 LLM，救不了知识检索节点。**

打开记忆后，LLM 记得用户在聊刘医生；但知识检索仍只用用户最新那句话去向量库里搜，它不知道"他"是谁。最终 LLM 没拿到资料，只能走兜底话术。

因此：**凡是有多轮指代的场景，必须在检索层做重写，而不是只给 LLM 开记忆。**

---

## 二、六类失效模式

### 1. 口语问法与文档用词不一致（语义鸿沟）

向量检索按相似度匹配，不理解同义。患者说"什么时候有号"，医院文档写"坐诊""出诊""排班"，字面完全不同，相似度得分过低，召回落空。

典型对照：

| 用户口语 | 文档官方用词 |
|---|---|
| 什么时候有号 / 什么时间能看 / 什么时候上班 | 排班、出诊时间、坐诊时间 |
| 看什么病 / 治什么病 | 擅长领域、诊疗范围 |

同一句话里"专家"能命中、"有号"命不中，就是典型症状：说明链路是对的，只是词汇没对齐。

### 2. 同义词、别名缺失

知识库里只写正式姓名，用户输入昵称、称谓、简称时召不回。别名必须显式写进语料（见第三节埋词）。

### 3. 重名条目 / 脏切片

源表格不规范时，同一个人会裂成多条切片。实测案例：搜"王明"返回 6 个切片，名称分别为"专家王明""急诊王明"，工号 1001、1002、1003 各不相同，**前 5 个切片内容全空**。

成因：Excel 存在隐藏行、合并单元格、排班表废弃字段。检索抽到空切片时，LLM 等于睁眼瞎。

### 4. 空内容条目

切片命中了，但核心字段为空。实测：`擅长1`、`擅长2` 有值，`简介:` 只有"副主任医师"四个字，`介绍:` 后面完全空白。

LLM 读到的信号是"资料里介绍为空"，于是判定无法回答，走兜底。这不是幻觉问题，是数据缺失。

### 5. 多轮指代丢失

用户在第三轮问"我应该看什么科室"，检索节点拿这 8 个字去搜，知识库不知道上文在聊"眼睛"，空手而归。

判断：如果同一问题在前一轮带上主语时能召回、单独问时不能，即为指代丢失。

### 6. 兜底话术过窄，把检索失败放大成体验事故

原始红线：`如果查不到，必须回复："抱歉，目前暂未收录该科室（或专家）的详细挂号信息。"`

用户问"详细介绍王明医生"，检索为空，模型一字不差复读这句带"挂号"的话，答非所问。

**兜底话术必须覆盖该类分支下所有可能的问法，不能预设单一场景。**

## 三、零延迟改善手段

原则：**能用数据（知识库）解决的，不要用算力（LLM 节点）解决。** 以下手段不增加任何节点，不增加延迟。

### 1. 知识库内埋词（首选，效果最直接）

在源表格字段名里直接写入口语同义词、别名。

```
修改前：出诊时间：周三上午
修改后：出诊时间（有号/坐诊/排班/上班）：周三上午
```

```
修改前：姓名: 刘语晗
修改后：姓名: 刘语晗（别名：南瓜）
```

做法：把患者/用户最常说的 3~5 个大白话词，用括号加进对应字段。检索命中率立刻上升，系统零负担。

### 2. 切换混合检索（Hybrid Search）

`知识检索` 节点 → 检索设置：

- 默认 `向量检索（Semantic Search）` → 改为 `混合检索（Hybrid Search）`
- 混合检索同时看"语义相似"与"字面命中"，对专有名词多、口语多的场景（医疗、政务、内部系统名）最有效
- 延迟不增加

### 3. 调整检索参数

| 参数 | 建议 | 说明 |
|---|---|---|
| `TopK` | 2 → 3 或 4 | 一次多捞几段给 LLM，宁可多看，不可漏召 |
| 相似度阈值 | 偏高时下调 | 阈值偏高会直接掐掉边缘命中 |

`TopK` 调大解决的是"知识库里明明有长篇内容却没被召回"，不是数据缺失。数据缺失调 TopK 无效。

### 4. 让分类器顺带产出检索关键词（一石二鸟）

分类器本来就要跑一次，让它同时输出改写后的检索词，几乎零额外延迟。

```text
请根据历史对话，判断用户的最新输入属于哪个分类（1/2/3/4）。
同时，提取出最重要的搜索关键词（把大白话转化为医疗术语，补全上下文的名字）。
请严格输出 JSON 格式：
{"class": "2", "keywords": "儿童保健科 刘惠娟 医生 排班 出诊时间"}
```

后续 `知识检索` 节点**不要用 `sys.query` 检索，改用该 `keywords` 字段**。

> 注意：JSON 结构化输出对模型能力有要求。若分类器用的是 mini/lite 级小模型，会触发 `invalid json object`（见 `intent-router.md`）。此时优先用埋词 + 混合检索，或换强模型后再上 JSON。

### 5. 组合建议

| 场景 | 推荐组合 |
|---|---|
| 追求绝对低延迟、高稳定 | 埋词 + 混合检索 + TopK 调大 |
| 多轮指代严重 | 追加分类器输出 keywords，或加问题优化节点 |
| 数据本身缺失 | 只能清洗知识库，参数与节点都救不了 |

## 四、问题优化节点（Question Optimizer）

作用：把用户简短、省略、带代词的话，结合对话历史补全为独立完整的检索问句。即 Query Rewrite。

### 1. 什么时候必须加

- 用户大量使用代词、省略句（"那怎么办""看什么科""他今天没来"）
- 业务需要把口语翻译成官方术语后才能召回
- 检索失败率集中在多轮对话的第二、第三轮

### 2. 代价

- 每次多一次模型调用，**增加 1~2 秒延迟**
- 语音/数字人场景下，这 1~2 秒的空窗体感明显
- 多一个节点 = 多一处变量引用要维护

### 3. 什么时候加了反而更慢

- 用户多为单轮完整提问，重写只是原样输出 → 纯浪费 1~2 秒
- 已用埋词 + 混合检索把召回率做到可用 → 重写的边际收益低于延迟成本
- 前置已有分类器输出 keywords → 功能重叠，重复改写

判断顺序：**先做埋词与混合检索，仍召不回再考虑加重写节点。**

### 4. 配置要点

| 项 | 配置 |
|---|---|
| 节点位置 | `开始` 与 `问题分类器` 之间 |
| 模型 | 便宜快速的小模型（如 Doubao-lite） |
| 记忆开关 | **必须打开**，否则无历史可补全 |
| 下游变量 | 分类器与知识检索的输入，`sys.query` 全部替换为问题优化节点的输出 |

替换变量是最容易漏的一步：只加了节点但下游仍引用 `sys.query`，等于没加。

### 5. 提示词模板

```text
你是一个负责优化用户搜索词的AI。
请根据【多轮对话历史记录】，将用户最新的一句话，补充为一个完整、独立、清晰的疑问句，以便于后续在知识库中进行准确搜索。

规则：
1. 如果用户的最新一句话已经很完整，直接原样输出。
2. 如果用户的最新一句话是代词或省略句（如"那怎么办"、"看什么科"、"他今天没来"），请结合历史对话，把缺失的主语、症状、业务名词补全。
3. 你【绝对只能】输出优化后的一句话，严禁输出任何多余的解释、寒暄或符号。

用户最新的一句话是：{{sys.query}}
```

### 6. 追加同义词替换规则（术语翻译）

在原规则后追加领域词汇映射，把大白话转成知识库官方用语：

```text
【专业词汇替换规则】：
为了提高知识库检索命中率，如果用户的话语中包含大白话，请在重写时自动替换或增加官方专业词汇：
1. 遇到"什么时候有号"、"什么时间能看"、"什么时候上班" -> 必须替换或补充关键词："排班"、"出诊时间"、"坐诊时间"。
2. 遇到"看什么病"、"治什么病" -> 必须补充关键词："擅长领域"、"诊疗范围"。

示例：
用户输入：那我挂儿童保健科，什么时间有号？
你优化的输出：儿童保健科的专家排班和出诊时间是什么安排？
```

## 五、记忆开关的能力边界

| 问题 | 记忆开关能否解决 |
|---|---|
| LLM 记不住上一轮说了什么 | 能 |
| 多轮对话中 LLM 把上文张冠李戴 | 能，前提是提示词不禁止引用上文 |
| 知识检索用代词去搜、召回为空 | **不能** |
| 口语用词与文档用词不一致 | **不能** |
| 知识库条目内容为空 | **不能** |

配置动作：`问题优化`、`LLM 2`、`LLM 3` 等所有需要多轮上下文的节点，逐个检查记忆开关是否打开。只开一个不够。

> 检查提示词里是否写了"每一轮对话均为独立处理，仅依据当前输入和召回知识回复"。该句与记忆开关语义冲突，可能让模型主动忽略上文，需删除或改写为"可结合上文指代理解本轮问题"。

## 六、知识库内容清洗

`Garbage In, Garbage Out`。智能体效果上限的绝大部分由知识库干净程度决定，节点配置只决定能否触及上限。

### 1. 清洗清单

| 问题 | 处理方式 |
|---|---|
| 同一实体裂成多条切片 | 把排班、职称、擅长、介绍合并到同一行 |
| 空切片（有名字无内容） | 直接删除，只保留有内容的那条 |
| 合并单元格、隐藏行、废弃字段 | 拆开合并单元格，删除空行与废弃列 |
| 核心字段为空（如 `介绍:` 为空） | 补全内容；确实无内容则在兜底话术里给出替代指引 |
| 同一字段多种写法 | 统一字段名与格式，避免切片结构不一致 |

### 2. 紧急修复 vs 源文件清洗

| 方式 | 适用 | 操作 |
|---|---|---|
| 平台 UI 内改 | 立刻要演示 | 在知识库条目界面删除空切片，直接编辑切片补内容，保存 |
| 源 Excel 清洗后重传 | 最终交付 | 去重合并 → 剔除冗余 → 补全信息 → 重新上传 |

**演示前用 UI 改，交付前必须回到源文件改。** 否则下一次重传知识库，脏数据全部回来。

### 3. 交付侧动作

客户提供的原始资料通常不规范。清洗责任要明确写进交付清单：谁提供源表、谁负责清洗、重传后谁验收。不要指望平台侧兜住脏数据。

## 七、检索结果如何进 LLM

`LLM` 节点有三个输入位，职责不能混：

| 位置 | 填什么 | 填错的后果 |
|---|---|---|
| 顶部【上下文】输入框 | `知识检索 / result`（`Array[Object]`） | 填 `sys.query` 会让 LLM 在资料夹里读到用户原话，判定"资料无相关内容"，回兜底 |
| SYSTEM 提示词 | 行为规则 + 用 `{{#context#}}` 或上下文变量气泡挂载顶部资料 | 不挂载则 LLM 不知道有资料 |
| USER 输入 | `sys.query`（用户真实提问） | 缺失则模型无法回应本轮问题 |

### 为什么要有独立的顶部上下文框

知识检索返回的是多个分段的数组，SYSTEM 只接受纯文本。顶部上下文框承担类型转换：接收数组，后台拼装为整齐纯文本，再通过变量气泡注入 SYSTEM。

**不要试图把知识检索的数组直接塞进 SYSTEM 文本里。**

### 上下文注入 vs Prompt 内嵌数据

| 方案 | 适用 | 优点 | 缺点 |
|---|---|---|---|
| 知识检索 + 顶部上下文注入 | 条目多、内容长、需持续更新 | 可扩展，改动在知识库侧 | 多一次检索耗时；有召回失败风险 |
| 数据直接写进 SYSTEM 提示词 | **10 条以内**的高频静态数据 | 命中率接近 100%；少一次检索，快约 1 秒 | 数据变了要改提示词并重新发布 |

实测：10 人以内的小名单走 RAG 时，因文本太短、阈值偏高导致召回失败；改为提示词内嵌后命中率从 50% 提升到 100%。

内嵌写法要求：给出完整对照表（姓名 + 别名 + 目标值），明确模糊匹配规则（含称谓"老师""总""哥""姐"），并约定无命中时的固定输出（如 `NONE`），供下游条件分支判断。

## 八、何时放弃知识库，改接口直连

知识库只适合**静态、低频变更**的内容。以下情况应改为接口直连或提示词内嵌。

### 1. 判断表

| 数据特征 | 方案 |
|---|---|
| 实时变化（号源、库存、工单状态、航班） | HTTP 接口直连，禁止放知识库 |
| 静态但条目 ≤ 10 条 | 直接写进 LLM 提示词 |
| 静态、条目多、内容长（科室介绍、专家简历、制度文档） | 知识库 |
| 需要精确字段与严格格式（邮箱、ID、金额） | 接口或提示词内嵌，不用检索 |

### 2. 动静分离架构

同一业务对象的不同属性可能走不同通道，按属性拆分分类：

| 分类 | 内容 | 通道 |
|---|---|---|
| Class 2：实时排班与号源查询 | 今天有没有号、号源剩余、星期几上班 | HIS / 业务接口 → LLM 播报 |
| Class 5：专家介绍与科室位置 | 简历、擅长、职称、科室在几楼 | 知识库 → LLM |

接口负责实时性，知识库负责丰富性。不要把两类问题塞进同一个分类，否则实时查询会拿到静态旧数据。

### 3. 改造步骤（从 RAG 切到提示词内嵌）

1. 删除 `知识检索` 节点
2. 上游节点输出直接连向 `LLM`
3. **清空 LLM 顶部【上下文】输入框**（残留的 `知识检索 / result` 必须点叉删除）
4. USER 输入接上游业务变量（如 `代码执行 解析表单 / target_person`）
5. SYSTEM 提示词写入全量对照表 + 匹配规则 + 无命中固定输出
6. 下游条件分支判断该输出是否等于无命中标记（如不包含 `NONE`）

## 九、排查顺序

按此顺序排查，不要跳步：

```text
前端表现不佳
  ↓
1. 连线是否正确（分支走对了吗）
  ↓
2. 节点变量是否传对（顶部上下文接的是知识检索结果吗）
  ↓
3. 提示词兜底话术是否过窄
  ↓
4. 知识检索是否真的召回了（看节点运行日志的召回片段）
  ↓
5. 召回为空 → 埋词 / 混合检索 / TopK / 问题优化
  ↓
6. 召回了但内容空 → 回到知识库清洗源数据
```

第 6 步之前的所有调参都无效。先确认数据是否存在。
