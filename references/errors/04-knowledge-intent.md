# 知识库与意图

覆盖症状：召不回来、分类器报错、意图分错、延迟高

条目 56–69（共 14 条）

## 知识库检索与意图路由

### 56. 问题分类器报 `got invalid json object. error: Extra data`

- **现象**：运行 `问题分类器` 节点时报错 `got invalid json object. error: Extra data`，工作流中断。
- **原因**：分类器底层是一次模型调用，平台强制要求只输出纯净 JSON。所选模型为 mini 级小模型（如 `Doubao-Seed-2.0-mini`），指令服从性弱，在 JSON 后追加了自然语言，例如 `{"class": "Class 3"} 好的，我已经为您分类好了！`，多出的文本破坏 JSON 结构导致解析失败。与连线逻辑无关。
- **解法**：优先换模型——把分类器模型从 mini 级换成参数更大、服从性更强的模型（`Doubao-pro`、`GLM-4`、`GPT-4o`、`Claude-3.5`），重跑。若平台锁定小模型，改防弹版：删除 `问题分类器`，换普通 `LLM` 节点只输出数字（`1/2/3/4`），后接 `条件分支`，判断条件用「包含 `1`」「包含 `2`」而非「等于」，即使模型输出"我觉得是类别 3 哦"也能正确流转。

### 57. 多轮对话中检索召回为空，但同一问题带上主语就能召回

- **现象**：第一轮问"孩子眼睛不舒服"能正常回答；第三轮问"我应该看什么科室"，LLM 回"抱歉，暂未收录"。同一句"孩子眼睛不舒服应该看什么科室"却能召回眼科信息。
- **原因**：`知识检索` 节点永远没有记忆，它只用用户最新那句话（"我应该看什么科室"）去向量库检索，不知道上文在聊眼睛，相似度不足，召回落空。LLM 拿不到资料，严格执行兜底话术。
- **解法**：在 `开始` 与 `问题分类器` 之间插入 `问题优化`（Question Optimizer / Query Rewrite）节点，选 `Doubao-lite` 级小模型，**必须打开记忆开关**，提示词要求把省略句补全为独立完整问句、只输出一句话。然后把 `问题分类器` 与 `知识检索` 节点里原本引用的 `sys.query` **全部替换为该节点的输出**。追求零延迟时改用知识库埋词 + 混合检索，或让分类器顺带输出 `keywords` 字段供检索使用。

### 58. 打开了记忆开关，知识检索仍然搜不到

- **现象**：确认各 LLM 节点记忆开关已开，多轮对话中 LLM 记得上文，但检索结果仍为空，最终回复"查不到"。
- **原因**：记忆开关只作用于 LLM 节点，让回答层记得上下文；`知识检索` 节点不共享这份记忆，依然用原始 query 检索。层与层之间不互通。
- **解法**：给检索层单独做重写（`问题优化` 节点，或分类器输出 `keywords`）。同时检查提示词里是否写了"每一轮对话均为独立处理，仅依据当前输入和召回知识回复"——该句与记忆开关语义冲突，可能让模型忽略上文，需删除或改写。逐个确认 `问题优化`、`LLM 2`、`LLM 3` 等所有需要上下文的节点都已开启记忆。

### 59. 用户问"什么时间有号"召不回来，问"有哪些专家"却能召回

- **现象**：问"儿童保健科有哪些专家"能完整答出专家与出诊时间；问"什么时间有号"直接回"抱歉，查不到"。
- **原因**：语义鸿沟（Vocabulary Mismatch）。向量检索按相似度匹配，不理解同义。用户说的是患者视角大白话"有号"，医院文档写的是"坐诊""出诊""排班"，字面完全不同，相似度得分过低导致落空。前半句能召回是因为文档里确实有"专家"二字。
- **解法**：三选一或叠加。① 知识库埋词（首选，0 延迟）：把源表字段改成 `出诊时间（有号/坐诊/排班/上班）：周三上午`；② 检索设置从 `向量检索（Semantic Search）` 改为 `混合检索（Hybrid Search）`，同时兼顾语义与字面命中，`TopK` 从 2 调到 3 或 4；③ 在 `问题优化` 提示词里追加术语替换规则，把"什么时候有号"映射为"排班/出诊时间/坐诊时间"。

### 60. 检索命中多个同名切片，且大部分内容为空

- **现象**：搜"王明"返回 6 个切片，名称为"专家王明""急诊王明"，工号 1001、1002、1003 各不相同，前 5 个切片内容全空。LLM 因此回"查不到详细介绍"。
- **原因**：客户提供的 Excel 不规范（隐藏行、合并单元格、排班表废弃字段），同一实体被拆成多条切片，并产生大量空切片。检索抽到空切片时 LLM 等于拿到空白资料。
- **解法**：紧急演示场景在知识库条目 UI 里直接删除空切片，只保留有内容的那条，并手动补全核心字段后保存。最终交付必须回到源 Excel：把同一实体的排班、职称、擅长、介绍合并到同一行，拆开合并单元格，删除废弃空行，清洗后重新上传。否则下次重传脏数据会全部回来。

### 61. 切片命中了，但核心字段是空的

- **现象**：问"详细介绍某医生"，检索有返回，LLM 仍回"暂未收录"。查看切片发现 `擅长1`、`擅长2` 有值，`简介:` 只有"副主任医师"四个字，`介绍:` 后面完全空白。
- **原因**：数据缺失，不是检索问题。LLM 读到"介绍：无"的信号，判定无法回答，走兜底。这属于幻觉控制正常生效，不是 bug。
- **解法**：补全字段内容（从医院公众号等公开渠道整理，或要求客户提供）；确实无内容时，把兜底话术改成通用表述并在其中给出替代指引（如"如需了解详细履历，请前往医院微信号查看"）。调 `TopK`、换检索模式对空字段无效。

### 62. LLM 明明接入了知识库，却总说"查不到"

- **现象**：知识库里明明有内容，检索日志也有召回结果，LLM 仍回复兜底话术。
- **原因**：`LLM` 节点顶部【上下文】输入框填错了变量——填成了 `@开始 / sys.query`，而不是 `@知识检索 / result`。相当于把用户原话塞进参考资料夹，LLM 打开资料夹看到的是"我要挂王丽华医生的号"，判定无相关资料。
- **解法**：清空顶部【上下文】里的 `sys.query`（点右侧叉号删除），点 `{x} 设置变量值`，选择紧邻上游的 `知识检索` 节点输出（`result`，类型 `Array[Object]`）。SYSTEM 里用 `{{#context#}}` 或上下文变量气泡挂载该资料。USER 输入保持 `sys.query` 不变。三者职责：上下文接收检索结果、SYSTEM 定行为规则并挂载资料、USER 接收用户真实提问。

### 63. 问"详细介绍某医生"却回复"暂未收录该科室的详细挂号信息"

- **现象**：用户要的是介绍，模型回复的却是挂号相关话术，答非所问。
- **原因**：兜底话术写得太窄。原始红线为 `如果查不到，必须回复："抱歉，目前暂未收录该科室（或专家）的详细挂号信息。"`，模型不懂变通，100% 复读，把预设的挂号场景强加到所有失败分支上。
- **解法**：把兜底话术改为覆盖该分支所有问法的通用表述，如"抱歉，目前知识库中暂未收录该专家的详细介绍或出诊排班信息"。同时按分类拆分不同兜底文案：超范围拒绝、知识缺漏、接口失败三类不复用同一段话。

### 64. 超范围提问（如"周杰伦老婆是谁"）被闲聊话术接走

- **现象**：用户问与业务完全无关的问题，机器人热情自我介绍"我是某某管家，很高兴为您服务"，边界感全无；或用户只打招呼"你好"，却收到冷冰冰的"知识库暂未收录"。
- **原因**：闲聊与超范围提问被合并成一个分类，下游只有一段话术，两类输入共用同一回复基调。
- **解法**：在 `问题分类器` 里拆成两类。Class 4「礼貌打招呼」——纯寒暄无具体问题，接固定欢迎话术（身份 + 服务范围 + 询问需求）；Class 5「超出范围无关提问」——有具体提问但与业务无关，接固定拒绝话术（声明服务边界 + 拉回业务范围）。各接一个 `直接回复` 节点，不新增 LLM 节点，零额外延迟。另注意第三类"业务问题但知识库无内容"要走业务分支的空结果兜底，不与前两类混用。

### 65. 分类器每次都要 1~2 秒，数字人开口前有明显空窗

- **现象**：用户说完话后 1~2 秒内系统无任何输出，数字人或语音端体感明显卡顿。分支内已挂垫话节点但无效。
- **原因**：延迟产生在分类器本身——它是一次模型推理，1~2 秒思考发生在业务分支之前。分支内的垫话位置太靠后，救不到最前面。
- **解法**：三类手段组合。① 快车道分流：在 `开始` 后直接接 `条件分支` 或 `代码执行` 做关键词匹配（约 2ms），把"厕所/wifi/快递/导航"等高频问题直接截胡到固定回复节点，绕过分类器，可覆盖约 70% 请求；② 口癖垫话：在分类器旁并行挂一个 `直接回复` 节点，内容只写"好的，"或"在的，"，前端 0.05 秒先出声，1.5 秒后业务内容接上，技术延迟被包装成思考顿挫；③ 给分类器减负：压缩分类描述到核心词（实测推理提速约 30%），锁死 `flash/mini/lite` 级模型，禁用 `max` 或带思考链模型。

### 66. 分类描述写得太长，分类又慢又不准

- **现象**：每条 CLASS 描述写了多行，包含大量业务背景与长示例；分类耗时高，且偶发分错。
- **原因**：模型分类时要把所有描述读入再算概率，文字越多思考越慢；同时描述之间语义重叠会让模型在边界样本上摇摆。
- **解法**：每条描述压缩为"核心场景词 + 1~2 个真实用户示例"，如把"询问公司介绍、餐厅、Wi-Fi密码、停车位、闲聊，如洗手间在哪……"压成"大堂设施、网络、问路、闲聊。"。删除业务背景描述，确保任意两条描述无语义重叠。分类数量按下游路径收敛，同一路径的合并。

### 67. 10 人以内的固定名单走知识库，召回率只有一半

- **现象**：把 10 人左右的名单放进知识库做检索，出现"南瓜""西南"这类别名时召回失败，命中率约 50%，且多一次检索耗时。
- **原因**：文本太短 + 相似度阈值偏高，向量检索对短文本、昵称类内容的召回不稳定。
- **解法**：删掉 `知识检索` 节点，把名单直接写进 `LLM` 的 SYSTEM 提示词（In-Context）。步骤：① 删除知识检索节点，上游直接连 LLM；② **清空 LLM 顶部【上下文】输入框**，残留的 `知识检索 / result` 必须点叉删除；③ USER 输入接上游业务变量；④ SYSTEM 写入完整对照表（姓名 + 常用别名 + 目标值）、模糊匹配规则（含"老师/总/哥/姐"等称谓）、无命中时固定输出 `NONE`；⑤ 下游 `条件分支` 判断输出是否包含 `NONE`。命中率可到 100%，且少一次检索约快 1 秒。

### 68. 问"儿科急诊在哪"却回复了一堆排班信息

- **现象**：查询位置时返回地点，但夹带号源排班内容；查询号源时又返回科室介绍。同一业务对象的两类问题互相串。
- **原因**：实时排班与静态介绍被分进同一个分类，走同一条链路。接口里没有简历字段，知识库里没有实时号源，两者都只能勉强作答并夹带无关内容。
- **解法**：在分类器做动静分离。Class 2「实时排班与号源查询」——仅限实时出诊、星期几上班、今天有没有号、号源剩余等动态信息，走参数提取 LLM → HTTP → 代码清洗 → 播报 LLM；Class 5「专家介绍与科室位置」——简历、擅长、职称、科室楼层等静态信息，走知识检索 → 播报 LLM。接口负责实时性，知识库负责丰富性。播报节点的提示词里再补一条"所答即所问：只问在哪就只答地点，不问号源不播报号源"。

### 69. 加了问题优化节点，检索结果没有任何变化

- **现象**：按方案插入了 `问题优化` 节点，多轮指代问题依旧，检索仍用原句。
- **原因**：只加了节点但下游变量没换。`问题分类器` 与 `知识检索` 节点仍在引用 `sys.query`，问题优化节点的输出无人使用。
- **解法**：断开 `开始 → 分类器` 的连线，改为 `开始 → 问题优化 → 问题分类器`；然后逐个打开 `问题分类器`、`知识检索` 等下游节点，把输入变量从 `sys.query` 替换为问题优化节点的输出文本。同时确认该节点的记忆开关已打开，否则无历史可补全。
