# 延迟与交互体验（Latency & UX）

适用：语音数字人、3D 大屏、具身智能体等对"听感延迟"敏感的场景。
前提：延迟无法归零，只能被"垫"掉或分流。先定位延迟发生在哪一段，再选补偿手段。

## 1. 延迟来源拆解

| 环节 | 典型耗时 | 触发条件 | 可压缩手段 |
|---|---|---|---|
| 问题分类器（LLM） | 1~2 s | 每个请求都要先分类 | 关键词快车道分流、压缩分类描述、换 flash/lite 模型 |
| 知识检索 | 依库规模与检索模式 | 命中知识库分支 | 混合检索（向量+BM25）+ Rerank 提精度，减少无效重查 |
| LLM 首 token | 200~300 ms（flash 级） | 每个 LLM 节点 | 选 flash/mini/lite；提示词要求首句极短 |
| 外部接口 | 1~2 s | 飞书消息、HTTP 请求、联网搜索（如博查） | 并行垫话、结果写死缓存 |
| 生图 / 重任务 | 4~8 s | CogView 等绘图 | 音画双轨，先出文本 |
| 代码节点 | 沙箱调用开销 | 每次执行 | 沙箱正常时可忽略；沙箱异常时会挂死（见 `deploy-ops.md`） |

定位判断：
- 用户在"刚说完"就感到卡顿 → 查分类器与首 token。
- 用户在"听到第一句之后"感到断裂 → 查外部接口与前端 TTS 队列。
- 用户感到"任务中断/黑屏" → 查数字人保活心跳与长任务链路。

## 2. 并行节点垫话法（Dify 1.17.x）

前提认知：`直接回复（Answer）` 是终点节点，右侧没有输出连接点。因此下面的串联不可能成立：

```text
【开始】→【直接回复: 正在查询…】→【调工具】→【直接回复: 结果】   ← 不可行
```

可行做法：用【+ 添加并行节点】，在慢分支入口挂一条并行的直接回复。

```text
              ┌── 路径 A（并行直接回复）：纯静态文本 ── 约 5 ms，经 SSE 最先到达前端
【分支触发】──┤
              └── 路径 B（重任务链路）：代码/查库/发飞书/调接口 ── 约 1500 ms，后台执行
```

执行要点：
- 路径 A 必须是写死的静态文本，不含变量、不经过 LLM，才能保证毫秒级先到。
- 路径 B 在垫话播报的 1~2 s 内并行跑完，结果由后续直接回复输出。
- 路径 A 先到 → 数字人立即开口；路径 B 结果后到 → 无缝衔接，听感延迟被抹平。

是否加并行垫话的判断：

| 分支耗时 | 典型节点 | 是否加 |
|---|---|---|
| > 1 s | 飞书消息、高德路线、外部 HTTP、联网搜索 | 加 |
| 300 ms ~ 1 s | 单次 LLM 生成 | 视体验要求，一般不加 |
| < 300 ms | 纯文本固定答复（如"请放右侧架子"） | 不加 |

## 3. 快慢车道分流

现状：分类器本身是 LLM，读完输入并推理出分支要吃掉 1~2 s。此阶段尚未进入业务分支，分支内的垫话救不到最前面。

做法：在【开始】后先放条件分支（关键词匹配，约 2 ms）截胡高频简单请求，只有长句、复杂请求才进大模型分类器。

```text
【开始】
   ↓
【条件分支：关键词快车道（约 2 ms）】
   ├── 包含(洗手间|厕所|wifi|密码) ──→ 【大堂问答】（约 10 ms，零等待）
   ├── 包含(快递|外卖|送餐) ────────→ 【外卖指引】（约 10 ms，零等待）
   ├── 包含(带我|导航) ─────────────→ 【物理带路】（约 10 ms，零等待）
   └── ELSE（复杂商务拜访、长句）───→ 【大模型问题分类器】（约 1.5 s）
```

分流判断：
- 意图唯一、答案固定、高频 → 走快车道，不进分类器。
- 含多条件、需澄清、涉及人名/表单/长句 → 走慢车道。

效果：高频问话彻底告别 1~2 s 延迟；只有真正复杂的请求才付那 1.5 s。

## 4. 口癖垫话

定义：垫话不用"正在为您查询"，改用人类思考时自然吐出的承接词。

可用词：`好的，` / `在的，` / `收到，`

与"正在为您查询"的差异：

| 维度 | "正在为您查询…" | "好的，" |
|---|---|---|
| 语义承诺 | 承诺"查询"。若下游只答"洗手间在左转"，逻辑违和 | 无承诺，任何下游答案都能接 |
| 听感归属 | 被识别为机器提示音 | 被识别为人类思考的顿挫 |
| 长度 | 长，占用 TTS 时长，与答案叠加显啰嗦 | 极短，不挤占答案 |
| 拼接效果 | "正在为您查询…洗手间在左侧" | "好的，（半秒停顿）洗手间在左侧拐角处" |

时间轴：

```text
第 0.05 s  并行直接回复吐出"好的，"，数字人立即开口
第 1.5  s  分类器推理完成，下游节点吐出正式答案
访客听感   "好的，（自然停顿）洗手间在左侧拐角处。"
```

要求：垫话节点内容只写 2~3 个字加一个逗号，不写完整句子。

## 5. 首句流式吐出

适用：必须拿到接口数据才能组织语言、无法提前垫话的链路。

做法：在调接口后的播报 LLM 提示词中强制"第一句是极短确认句"。
- 示例首句：`已为您查询到最新天气情况：`
- 机制：Dify 流式输出（Stream），首句几十毫秒先到，数字人拿到前几个字即可开口发音。
- 与并行垫话的关系：二选一。同时使用会造成两句开场叠加。

## 6. 何时不该垫话

| 场景 | 处理 | 误加后果 |
|---|---|---|
| 分支本身 < 300 ms 的纯文本答复 | 不加并行垫话 | 数字人连发两条重复问候，像结巴 |
| 答案是"洗手间在哪""请放右侧架子"这类无需查询的问题 | 不用"正在为您查询" | 答非所问，违和 |
| 已配置首句流式确认句 | 不再加并行垫话 | 开场重复 |
| 垫话文案与分支实际内容矛盾 | 改文案或删节点 | 用户困惑 |

原则：垫话只服务于"真的在等"的链路。链路越短，越不要加。

## 7. 前端 TTS 播放队列配合要求

现象：使用并行回复后，Dify 会在同一会话流里几乎同时下发两段文本（垫话 + 最终结果）。

向前端 / Unity 研发提出的要求（可直接转述）：

```text
工作流中配置了原生并行垫话流。前端 TTS 收到第一段（如"好的，"）时立即播放；
收到第二段最终结果时，将音频加入播放队列，等第一段播完后平滑连贯播放，
禁止截断第一段。
```

验收：连续触发 10 次慢分支，确认无截断、无两段重叠、无超过 300 ms 的静音空档。

## 8. 数字人长任务中断的解法（音画双轨）

现象：生图需 4~8 s，期间模型不发声，客户端保活心跳（Keep-Alive）超时，判定任务中断甚至死机。

解法：从开始节点拉两条并行分支，声音轨先出声，视觉轨后台出图。

```text
              ┌── 轨道 A（声音轨，约 0.3 s 出声）：【LLM 绘本故事创作】→【直接回复 1：播报故事】
【用户输入】──┤
              └── 轨道 B（视觉轨，后台异步）：【COGVIEW 绘图】→【代码执行】→【直接回复 2：弹图信令】
```

轨道 A 配置：
- 模型：`qwen3.5-flash`（首字延迟 200~300 ms）。
- USER：`{{开始 / query}}`。
- SYSTEM 约束：纯文本、禁止 Markdown 标记、禁止动作描写括号、80~120 字（朗读 10~15 s）。

轨道 B 配置：
- 生图节点 → 代码执行节点提取图片 URL → 直接回复 2 输出信令：

```text
widget_pic_start:{__image_url:{{代码执行 / image_url}}}:widget_pic_end
```

运行时序：

| 时间 | 事件 |
|---|---|
| 0.3 s | 轨道 A 出声，心跳被激活，不会超时中断 |
| 4.5 s | 数字人仍在讲述，轨道 B 生图完成、代码节点吐信令 |
| 之后 | 屏幕按信令淡入插画 |

判断：
- 下游含生图、大文件解析、> 3 s 的接口 → 必须拆双轨。
- 全部节点 < 1 s → 单轨即可，不要为好看硬拆。

## 9. 分类器性能压榨

仅在必须用大模型分类时执行：
- 压缩分类描述：把"询问公司介绍、餐厅、Wi-Fi 密码、停车位、闲聊，如洗手间在哪……"压成"大堂设施、网络、问路、闲聊"。描述字数减半，推理速度约提升 30%。
- 锁死小参数模型：分类器只用 flash / mini / lite（如 `qwen3.5-flash`、`Doubao-lite`），不要用 max 或带思考能力的模型。
- 结构化输出：需要机器消费的字段走 `structured_output`，不要用 `text` 再二次解析。

- [ ] 无快分支误挂垫话。
- [ ] 未同时使用并行垫话与首句确认句。
