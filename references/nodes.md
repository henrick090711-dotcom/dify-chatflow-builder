# 节点配置要点与画布编排（Dify Chatflow / 某智能体平台）

适用：搭画布前先查第 1 节速查表，配节点时查对应小节，连线前查第 13 节。

---

## 1. 节点速查表

| 节点 | 必填项 | 输出变量形态 | 高频失效 |
| :--- | :--- | :--- | :--- |
| 开始（Start） | 输入参数、参数类型、参数描述 | `sys.query` + 自定义参数 | 只留一个模糊参数，下游信息残缺 |
| LLM | 模型、SYSTEM、USER、记忆开关 | `text`（String）；开结构化输出后多 `structured_output`（Object） | 忘插 `sys.query`，模型无题可答 |
| 知识检索（Knowledge Retrieval） | 知识库、Query、TopK、检索模式 | `result`（Array[Object]） | Query 用 `sys.query` 导致指代丢失 |
| 问题分类器（Question Classifier） | 模型、分类描述、各类名 | 分支出口 Class 1..N + 默认 ELSE | 小模型输出多余字符，`invalid json object` |
| 条件分支（IF/ELSE） | 变量、比较符、值、逻辑关系 | IF / ELIF / ELSE 出口 | 多个值塞进一个输入框，条件永不命中 |
| 代码执行（Code） | 输入变量名+值、输出变量登记、Python3 代码 | 自定义登记名 | return key 与登记名不一致 |
| HTTP 请求 | Method、URL、Headers、Body | `body`、`status_code` | Body 缺外层双引号、Header 含中文 |
| 模板转换（Template） | 至少 1 个输入变量、模板正文 | `result`（String） | 未绑输入变量，校验不过 |
| 变量赋值（Assign Variable） | 目标会话变量、覆盖或设置、值 | 无输出（副作用节点） | 框内写方程式，值被当纯文本 |
| 直接回复（Answer） | 回复内容（文本或气泡） | 无输出 | 把带暗号的原始 `text` 直接回给用户 |
| 结束 / 输出（End） | 输出变量名 + 值 | 无输出 | 任务型工作流里想直接打字，但只能选变量 |
| 工具节点（插件） | 授权、输入变量、消息体格式 | 工具返回字段 | 消息体不是 JSON 序列化字符串 |

---

## 2. 开始节点

必填：

- 输入参数名、类型（String / Number 等）、中文描述。描述会作为工具调用时的字段语义，必须写具体。
- Chatflow 默认带出 `sys.query`，无需手工新增。

易错：

- 只留一个模糊参数（如 `mingzi`），导致下游通知内容残缺，还被迫加一个 LLM 提取节点。
- 参数名用中文或带空格，工具调用时字段对不上。
- 参数无描述，主 Agent 无法自动对号入座。

判断分支：上游能给结构化字段 → 拆成多个明确参数，删掉 LLM 提取节点；上游只给自然语言 → 保留 LLM 提取。

---

## 3. LLM 节点

必填：

| 区域 | 内容 |
| :--- | :--- |
| 顶部模型 | 严格格式输出（分类、提取、JSON）用大参数量模型；闲聊可用小模型 |
| 顶部【上下文】 | 仅放知识检索的 `result`，用于自动转纯文本 |
| SYSTEM | 角色、规则、输出格式；变量一律用 `{x}` 插气泡 |
| USER | 必须插 `sys.query` 气泡 |
| 右侧【记忆】 | 多轮场景必须打开 |

易错：

- 只写 SYSTEM 不写 USER，模型回答"我懂了"。Chatflow 不会自动传用户输入。
- 在 SYSTEM 里手打 `quiz_topic = sys.query`，模型把代码念出来。
- 把 `sys.query` 塞进顶部【上下文】，挤掉了知识库资料。
- 需要多轮记忆的节点漏开记忆，模型记不住上一轮考了什么。
- 期望 LLM 输出 JSON 后条件分支能选 `is_complete`：不可能，LLM 只暴露 `text`。

输出形态：`text`（String）。开启结构化输出后多一个 `structured_output`（Object），需展开子字段才能取到具体值（如 `structured_output.json_path`）。取子字段时必须点开 `>` 二级菜单，不要选第一行的 `text`，否则拿到的是带花括号和换行的整段 JSON。

---

## 4. 知识检索节点

必填：

- 知识库选择（一个或多个）。
- Query：必须是已归一化的检索词，不能是带代词的原始问句。
- 检索设置：TopK（默认 2，召回不足调到 4）；检索模式（向量检索 / 混合检索）。

易错：

- Query 直接绑 `sys.query`。用户说"他什么时候有号"，检索器不知道"他"是谁，返回空。
- 召回为空时把空白 `{{#context#}}` 喂给模型，模型只能编。
- 用检索模式解决口语与术语的映射（"有号" vs "排班"）：优先在知识库原文里埋词，或改混合检索，不要盲目加节点。

修法（三选一，按延迟敏感度）：

1. 知识库语料埋词：`出诊时间（有号/坐诊/排班/上班）：周三上午`，零延迟。
2. 检索模式改混合检索，TopK 调到 4。
3. 在分类器或前置 LLM 里同时输出 `keywords`，检索用 `keywords` 而不是 `sys.query`。

输出形态：`result`（Array[Object]）。不能直接插进 SYSTEM，必须放 LLM 顶部【上下文】。

## 5. 问题分类器节点

必填：

- 模型：必须用服从指令能力强的大模型。分类器底层是一次 LLM 调用，平台要求其只输出纯净 JSON（形如 `{"class": "Class 3"}`）。
- 每个 Class 的名称与描述。描述不是备注，就是分类 Prompt，必须写互斥规则和举例。
- 默认分支（ELSE）的归宿。

易错：

- 用小参数量模型（如 Seed-mini 类），输出 `{"class": "Class 3"} 好的，我已经为您分类好了！`，平台解析失败报 `invalid json object`。
- 分类边界模糊：用户问"什么时候有号"，被分到"直接发二维码"而不是"查排班"。解法是在 Class 描述里加互斥规则与反例。
- 分支数不够用时硬塞语义，导致一个 Class 承担两种业务。

两种实现方式：

| 方式 | 做法 | 稳定性 |
| :--- | :--- | :--- |
| 平台分类器节点 | 换大模型，写好各 Class 描述 | 高，但依赖模型服从性 |
| LLM + 条件分支手搭 | LLM 只输出数字 1/2/3/4，条件分支用"包含"抓数字 | 最高，小模型抽风也能兜住 |

手搭版条件分支配置：

```text
CASE 1 (IF)   : LLM.text 包含 1 -> 知识库答疑
CASE 2 (ELIF) : LLM.text 包含 2 -> 模拟陪练
CASE 3 (ELIF) : LLM.text 包含 3 -> 专项训练
CASE 4 (ELIF) : LLM.text 包含 4 -> 复盘报告
默认 (ELSE)   : 礼貌兜底
```

---

## 6. 条件分支节点

必填：

- 每个 CASE 的变量（用气泡选）、比较符（等于 / 包含 / 不包含 / 为空 / 正则等）、值。
- CASE 之间的逻辑关系（AND / OR）。
- 默认分支 ELSE 的归宿。

匹配逻辑与常见失效：

| 现象 | 根因 | 修法 |
| :--- | :--- | :--- |
| IF 明明该命中，却总走 ELSE | 把 `[SUCCESS] 或 [FAIL]` 整串填进一个输入框，系统去找这整句话，找不到 | 拆成两个条件，中间选"或（OR）" |
| 输出里有 SUCCESS 仍不命中 | 模型输出带 Markdown 修饰，`[SUCCESS]` 与实际字符不一致 | 只填纯大写字母 `SUCCESS`，去掉中括号 |
| 同一分支既结束又继续 | 模型同时输出新问题和 `[END]` | 提示词强约束"二选一"，禁止同时出现 |
| 找不到上游 JSON 字段 | LLM 只暴露 `text` | 改为"包含标记词"方案 |

状态机写法（主控分支）：

```text
CASE 1 (IF)   : current_mode 等于 rp_setup   -> 陪练配置
CASE 2 (ELIF) : current_mode 等于 rp_active  -> 陪练对战中
CASE 3 (ELIF) : current_mode 等于 quiz_setup -> 训练配置
CASE 4 (ELIF) : current_mode 等于 quiz_active-> 训练对战中
默认 (ELSE)   : 去意图识别 / 问题分类器
```

每个 CASE 出口必须紧跟【变量赋值】改状态，再进【直接回复】。只回复不改状态，闭环不退出。

标记词方案（无法读 JSON 字段时的标准解）：让 LLM 在信息齐备时输出 `[ALL_COMPLETE]` + JSON，未齐备时只输出纯人话；条件分支用 `text` **包含** `[ALL_COMPLETE]` 判定。这样 ELSE 分支直接把 `text` 回给用户，不会把 JSON 喷到屏幕上。

## 7. 代码执行节点

必填：

| 项 | 要求 |
| :--- | :--- |
| 语言 | Python3 |
| 输入变量 | 变量名有意义（`llm_text` / `user_query` / `kb_text` / `http_result`），右侧用 `{x}` 绑气泡，不可留空 |
| 输出变量 | 在【输出变量】区点 `+` 登记，类型默认 String |
| 函数签名 | `def main(**kwargs)`，用 `kwargs.get("变量名", 默认值)` 取值；也支持 `def main(arg1)` 配 dict 取值 |
| 返回 | `return {"登记名": 值}`，key 与登记名逐字一致 |

运行环境限制：

- 沙箱隔离执行，有超时控制。代码里做长时间等待或死循环会一直转圈直到超时报错。
- 不要指望在代码节点里发网络请求。需要调接口时用【HTTP 请求】节点，代码只做前后的拼装与清洗；沙箱死等网络响应会把任务卡在 `running`。
- 第三方库不可依赖，只用标准库（`json`、`re`、`urllib.parse` 等）。
- 入参类型由界面决定：选 `text` 得到字符串，选 `json` 直接得到 dict 或 list（`Array[Object]` 时先判 `isinstance(raw, list)` 再取 `[0]`）。

必写容错：外层 `try/except`，异常分支也要返回同名 key，并给出兜底文案。

```python
import json, re

def main(**kwargs):
    raw_text = str(kwargs.get("llm_text", ""))
    target, v_name, v_phone = "相关老师", "贵宾", "未留"
    try:
        m = re.search(r'(\{[\s\S]*\})', raw_text)
        if m:
            d = json.loads(m.group(1))
            target = d.get("target_person") or target
            v_name = d.get("visitor_name") or v_name
            v_phone = d.get("visitor_phone") or v_phone
    except Exception:
        pass
    return {"final_output": f"{target}|{v_name}|{v_phone}"}
```

用代码替代 LLM 的场景：字段固定、规则确定、需要毫秒级响应（如拼飞书卡片、校验白名单、手机号脱敏）。手机号脱敏一行：`phone[:3] + "****" + phone[-4:] if len(phone) == 11 else phone`。

## 8. HTTP 请求节点

必填：

| 项 | 示例 |
| :--- | :--- |
| Method | 与接口文档一致，`POST` 不能写成 `GET` |
| URL | 完整地址，含端口；不要留 `ip:端口` 占位 |
| Headers | `Content-Type: application/json`；需要伪装浏览器时补 `User-Agent` |
| Body | 勾选 `JSON`，按接口文档写结构；字符串化 JSON 字段内的引号要转义 |

易错：

- Body 里嵌套字符串少转义：`"data": "{\"keyWord\":\"xxx\"}"` 中的内层双引号必须带反斜杠。稳妥做法是用前置代码节点 `json.dumps()` 生成该字符串，HTTP 里只写 `"data": "{{代码1.his_data_string}}"`。
- Header 填中文直接崩溃。HTTP 头只允许 ASCII，中文参数一律放 Body。
- 传整段 `text` 给需要精确值的 Header（如 `X-JSON-Path`），拿到带花括号和 `\n` 的 JSON，请求头当场报错。要用 `structured_output` 的二级子字段。
- 报 `405 Method Not Allowed` 说明请求已到服务器但方法/路径被拒，先核 Method 与 URL，再怀疑平台配置。
- 内网接口需要鉴权头或白名单，缺一个就返回 401/403 或空白 HTML。

输出形态：`body`（接口原始返回，通常是字符串）、`status_code`。`body` 后面接代码节点清洗，再接 LLM 播报，避免把整坨 JSON 喂给模型浪费 Token 且易看错。

## 9. 模板转换节点（Template / 文本处理）

必填：

- 至少一个输入变量（左侧变量名 + 右侧绑气泡）。没有输入变量时校验不通过。
- 模板正文。语法为 jinja2，动态值写 `{{变量名}}`。

用途：

| 场景 | 说明 |
| :--- | :--- |
| 变量拼接 | 唯一可靠的"旧值 + 新值"拼接方式，配合【变量赋值】覆盖模式写回 |
| 任务型工作流补文案 | 输出节点只能选变量，用模板节点把固定话术打包成 `message` 变量 |
| 文案动态化 | 绑 `name` 后写 `好的，已经通过飞书为您通知了 {{name}} 老师` |

易错：

- 忘记绑输入变量，节点校验红叉。
- 在模板里手打节点名（如 `{{LLM 4.text}}`）而不是绑气泡，取不到值。

输出形态：`result`（String）。引用时用气泡选。

---

## 10. 变量赋值节点

必填：

- 目标会话变量（在下拉里选，不能手打）。
- 模式：覆盖（只能选一个变量）/ 设置（只有文本框，`/` 与 `{x}` 均被屏蔽）。
- 值：常量写纯值，变量用覆盖模式选气泡。

易错：

- 框里写 `current_mode = idle`，值被当纯文本，状态永远不等于 `idle`。
- 手打 `{{weakness_log}}` 或字面 `\n`，不生效。
- 用设置模式做拼接，插不进气泡。
- 只改业务变量不改状态机变量，闭环不退出。

输出形态：无输出。它是纯副作用节点，下游只能通过引用会话变量拿到新值。详细规则见 `references/variables.md`。

---

## 11. 直接回复节点（Answer）

必填：回复内容，可以是手打文本，也可以是变量气泡。

易错：

- 把上游 LLM 的原始 `text` 直接回显，导致 `[SUCCESS]`、`[END]`、JSON 代码漏到用户屏幕。
- 需要拼接固定文案与模型输出时，直接在框里组合：先手打固定文案，再 `{x}` 插 `LLM.text` 气泡，末尾加分割线弱化残留标记。
- 多分支共用同一个回复节点时忘记区分成功/失败文案。

输出形态：无输出。

---

## 12. 结束节点 / 输出节点（Workflow）

判断分支：

- Chatflow（对话型）→ 用【直接回复】收尾，可以直接手打文字。
- Workflow（任务型）→ 用【输出】节点，**只能选变量，不能直接打字**。

任务型工作流要给前端一段固定中文话术时，标准做法：

```text
条件分支 ->【模板转换 查无此人文案】->【输出 message = {{查无此人文案.result}}】
条件分支 ->【发送飞书】->【模板转换 发送成功文案】->【输出 message = {{发送成功文案.result}}】
```

易错：在输出节点里找"直接输入文本"的入口，找不到是正常的，改用模板转换节点。

## 13. 工具节点（以飞书应用消息为例）

必填：

| 项 | 要求 |
| :--- | :--- |
| 授权 | 工作区 API ID / Key 配好后仍需节点侧确认授权，未授权时输入框不展开 |
| 接收者 ID 类型 | `open_id` / `email` / `chat_id` |
| 接收者 ID | 用 `email` 时直接填企业邮箱，比找 `ou_` 开头的 open_id 省事 |
| 消息内容 | 必须是 JSON 结构序列化后的字符串 |

消息体格式（飞书文本消息硬性要求）：

```json
{"text": "【前台来访提醒】\n您好，前台检测到有访客正在找您！\n- 访客姓名：{{开始/visitor_name}}\n- 联系电话：{{开始/visitor_phone}}\n请及时前往接待。"}
```

易错：

- 直接在消息内容里打一句中文，接口拒绝发送。必须包在 `{"text": "..."}` 里。
- 花括号内用 `/` 插气泡，不要手打变量名。
- 插件抽风时改用【HTTP 请求】直连 Webhook：`POST` + `Content-Type: application/json` + Body `{"msg_type":"text","content":{"text":"..."}}`，零插件依赖。

## 14. 节点顺序与连线原则

必须串行（有数据依赖，不能并行）：

- 变量赋值 → 使用该变量的条件分支或节点。
- 知识检索 → LLM（上下文依赖）。
- 代码清洗 → LLM 播报（清洗结果依赖）。
- LLM 提取 → 条件分支（分支依赖其 `text`）。
- 开始 → 状态机条件分支（第一跳必须先判状态，再判意图）。

可以并行（无数据依赖）：

- 静态垫话与重链路并行。用户触发慢操作时，从分支入口挂一条并行【直接回复】说"好的，正在为您通知对接老师，请稍候"，主链路继续跑飞书/地图/接口。
- 只有慢分支才挂并行：调飞书（1~2 秒）、调地图、查复杂接口。纯文本快分支（如"外卖请放右侧架子"）不要挂，否则连续两条重复问候。
- 并行回复下发的是两段文本，需前端 TTS 排队播放，第二段不要截断第一段。

连线纪律：

- 每条分支都要有归宿，收敛到【直接回复】或【结束】。悬空节点不会执行。
- 一个节点多个出口时，先确认出口语义再连线，IF/ELIF 顺序影响命中优先级。
- 加节点时插入而非重连：先断开目标连线，插入新节点，再前后各连一次，避免漏连。
- 状态机在前、意图识别在后，避免陪练/登记中被闲聊打断。

## 15. 重命名与画布注释规范

节点重命名（右侧面板顶部可改）：

- 统一格式：`类型 (业务语义)`，例：`LLM (航班播报话术生成)`、`工具 (AOC 航班数据库查询)`、`代码 (拼装面试卡片)`、`模板 (发送成功文案)`。
- 默认名 `LLM 4`、`变量赋值 7`、`代码执行 2` 只允许出现在调试期。交付前全部改成语义名，否则分支一多无法排查。

节点内描述（右侧面板"添加描述"）：

- 一句话写清输入与职责，例：`接收旅客输入的自然语言问询（航班号、目的地、航司、时间），作为查询基准输入。`
- 写清关键约束，例：`将口语归一化为纯 ASCII 的 JSONPath 表达式。`

画布便签（左侧"添加注释/便签"）：

- 放在画布左上角做全局说明：业务目标、关键依赖、需要替换的配置项。
- 放在关键节点下方做参数说明：该节点的输入来源、输出去向、易错提醒。
- 便签按语义分色，同一业务分支用同色，便于一眼看出模块边界。
